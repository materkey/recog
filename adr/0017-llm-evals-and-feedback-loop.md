# ADR-0017: E2E-оценка, трассировка и HITL для AI-саммари

## Status
Proposed

## Context
AI-анализ встреч (ADR-0013) сейчас опирается на один промпт и не гарантирует:
- стабильный формат и воспроизводимость результата;
- защиту от галлюцинаций на длинных/шумных транскриптах;
- быстрый цикл улучшений (нет трассировки, eval-набора, регрессий).

На практике качество чаще ломается из‑за контекст‑сборки, чанкинга и постобработки,
а не из‑за текста промпта. Нужен инженерный цикл, где тестируется сервис целиком,
а не отдельный prompt.

## Decision

### 1. Контракт результата: строгий JSON + evidence
Вывод для summary обязателен в JSON и содержит:
- `summary` (краткие буллеты);
- `decisions`, `action_items`, `open_questions`, `risks`;
- для `decisions`/`action_items` обязательное поле `evidence` с ссылками на
  `segment.id` из `transcript.jsonl` и/или таймкодами.

Если владелец/дедлайн не встречается в транскрипте — возвращается `null`.

### 2. Контекст‑пайплайн вместо “одного промпта”
Длинные транскрипты обрабатываются пайплайном:
1) normalize → единый формат `(time, speaker, text)`
2) segment → смысловые границы (смена темы/спикера/паузы)
3) extract (map) → кандидаты решений/задач/фактов + evidence
4) merge (reduce) → дедупликация и согласование
5) write → финальный summary только из extract-слоя

### 3. Трассировка каждого запроса (LLM trace)
Для каждого вызова AI сохраняем:
- `prompt_version`, `context_builder_version`
- модель и параметры (temperature, max_tokens, top_p)
- список сегментов, вошедших в контекст
- assembled prompt (или шаблон + подстановки)
- сырое и нормализованное ответы
- latency/tokens/cost
- `meeting_id`, язык, длина

### 4. Evals: сервис под тестом
Offline‑регрессии в CI вызывают API сервиса, а не “скрипт промпта”.
Минимальный набор проверок:
- JSON‑schema валиден
- обязательные поля заполнены
- evidence присутствует и указывает на реальные `segment.id`
- запрет на “придуманные” владельцев/дедлайны

LLM‑judge применяется только для pairwise/regression и валидируется на ручных метках.

### 5. Human‑in‑the‑loop по умолчанию
UI предоставляет действия:
“принять / исправить / ошибка + причина (5–7 категорий)”.
Правки сохраняются как diff и пополняют eval‑набор.
Ответственный за качество — один доменный эксперт (benevolent dictator).

### 6. Guardrails vs evaluators
Inline guardrails: JSON‑валидность, PII‑редакция, запрещённые паттерны.
Evaluator’ы (faithfulness/coverage) запускаются асинхронно на выборке прод‑трафика.

### 7. Релиз и мониторинг
Feature flags, canary, shadow‑прогоны для сравнения версий.
Online‑мониторинг качества отделён от CI‑регрессий.

## Implementation

### Компоненты
- `PromptRegistry` и `ContextBuilder` для версионируемого контекста
- `TraceStore` для LLM‑трасс
- `Evaluator`/`Replay` для прогонов и сравнения
- `FeedbackStore` для правок пользователей

### Хранение (пример)
```
meetings/{id}/transcript.jsonl
meetings/{id}/ai_traces.jsonl
meetings/{id}/ai_feedback.jsonl
```

## Consequences

### Positive:
- Воспроизводимость и быстрые регрессии
- Меньше галлюцинаций за счёт evidence
- Чёткий цикл улучшений (offline + online + HITL)

### Negative:
- Рост сложности и объёма хранимых данных
- Потребность в регулярной ручной разметке

### Mitigation:
- Начать с минимального eval‑набора (50–100 встреч)
- Ограничить объём трассировок sampling’ом

## Alternatives Considered
1. **Промпт‑тестирование в вакууме** — отклонено, не покрывает контекст/чанкинг.
2. **Один проход “summary за раз”** — отклонено, плохо на длинных транскриптах.
3. **Готовые метрики (ROUGE/BERTScore)** — отклонено, не отражают реальных ошибок.

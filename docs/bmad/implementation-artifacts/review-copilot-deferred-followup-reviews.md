  evidence: At HEAD BASE_REVISION, `recog/web/bridge_subscriber.py:166-171` (`ws = self._ws … await ws.send(raw)` — no per-send bound); called from `recog/web/server.py:546` (`sent = await subscriber.send(raw)`), which is awaited inline in the `/api/live/stream` receive loop at `recog/web/server.py:1547-1549`. ## BASE_REVISION — sweep dw-bridge-fanout-send-timeout (DW-6)

- source_spec: `_bmad-output/implementation-artifacts/spec-copilot-deferred-followup-reviews.md`
  summary: BASE_REVISION's `copilot_chat_message` forward discards `_send_bounded`'s delivered result, so when every Copilot channel socket times out (or is already fail-fast-marked in `_timed_out_clients`) the request is silently undelivered while its pending entry stays in `_copilot_pending_requests` — the asking UI gets no echo for the bounded window until the stalled socket's reap fires the 1→0 channel-client transition (which pops pending entries and broadcasts a terminal `channel_disconnected`), and hangs permanently in the narrower case where another channel client connects before the reap so the count never reaches 0 — unlike the empty-channel branch, which replies `channel_disconnected` up front, and unlike `_relay_to_supervisors`, which uses the same boolean to drive a `supervisor_disconnected` echo.
  evidence: At HEAD BASE_REVISION, `ktalk_bridge.py:3097-3109` — `forward()` does `await self._send_bounded(client, outbound)` (`:3099`) with the return value ignored, then `asyncio.gather(...)` with no delivered tracking; `ktalk_bridge.py:3095` `self._copilot_pending_requests[request_id] = meeting_id or ""` is set just before and never rolled back; contrast `ktalk_bridge.py:1335` `if await self._send_bounded(client, message): delivered = True` and the zero-clients `channel_disconnected` echo at `:3052-3068`. The gap is normally bounded: `_send_bounded`'s timeout schedules `close()`, and the handler reap's 1→0 channel-client transition at `ktalk_bridge.py:2205-2221` pops all non-stale pending entries and broadcasts a terminal `channel_disconnected` `copilot_status` — but (a) between forward-failure and that reap the UI shows nothing actionable, and (b) if another channel client connects before the stalled one is reaped, the count never reaches 0, the pop never fires, and the undelivered request's pending entry stays live indefinitely. Not a duplicate: DW-8 (resolved) and the spec-bridge-copilot-reply-guards bullets all concern reply-side drops or pending-entry invalidation on session-death paths — none covers forward-time delivery failure; the pre-BASE_REVISION code had no delivered signal to check (a stalled socket hung the handler instead), so discarding the new signal is introduced by this diff.

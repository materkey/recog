### Observations (Task 4 of `docs/plans/2026-04-24-per-speaker-refine-rollout.md`)

- **Acceptance vs plan §4.3**:
  - Delta negative on both tracks — PASS (-4.3% track 1, -3.3% track 2).
  - ⚠️ Refined WER ≤ 25% on at least one track — **MISSED**. Both tracks land at 32.6%, roughly 7.6 ppts above the target. Per plan §5.5, this WER miss means **do not flip `RECOG_PCM_REFINE` default to `1`**. Keep default `0`; let the user decide after operational validation in real meetings.

- **Refined segments ratio**: 7 of 16 live segments rewritten per track. The remaining 9 keep the original live text because their audio sits inside the still-growing 20 s refine window at benchmark shutdown. Two forces drive when a segment enters a refine window:
  - `SPEAKER_TURN_GAP=3 s` of PCM silence — the replay has no internal gaps, so this only fires once at the trailing silence injected by `_drain_until_idle`.
  - `PCM_REFINE_MONOLOG_CAP_S=15 s` monolog cap — fires ~3× over a 48 s trim (every 15 s of continuous speech).

  Net: ~4 refine cycles × ~2 closed segments per cycle ≈ 7 refined. In real meetings this is less of a concern — turn-boundaries are the dominant trigger and virtually every closed reply gets refined.

- **Baseline shift from grid-search (`2026-04-23-gigaam-grid.md` = 33%)**: live WER here is 36.4% avg (~3 ppts worse). Likely causes: (a) the full pipeline (`PerSpeakerIngest` batching + chunked PCM ring) fragments utterances across 3 s chunks whereas the grid-search transcribes each trim in a single call; (b) each 3 s chunk is transcribed without cross-chunk context, so boundary errors (e.g. "Погулять" dropping the preceding "Вышел зайчик") accumulate.

- **Edge cases observed**:
  - Chunk-boundary truncation in live: track 2 emits `"умирает за"` (cut mid-word) — refine later produces `"Умирает зайчик мой"` with the proper word boundary. This is the headline gain the contour was designed for.
  - Sanity filter: no rejected refine applies observed (would show as an unchanged segment despite a refine pass). Both tracks' refined windows overlap live segments cleanly.
  - Empty word list: none seen; every refine cycle emitted ≥ 1 word.
  - Identical-text skip: not triggered — refine always changed at least one boundary segment per cycle.

- **Recommendation**: keep `RECOG_PCM_REFINE=0` default. Refine produces a consistent, modest WER improvement (-3.8% avg) but does not hit the ≤ 25% gate on synthetic fixtures. Real meetings with natural turn-taking should perform better (more refine firings per minute), which is what the user-driven operational validation (plan §12.6) is designed to measure.

### Latency Observations (Task 5 of `docs/plans/2026-04-24-per-speaker-refine-rollout.md`)

- **Acceptance vs plan §5.3**: Δ p95 = **+23.4 ms**, well under the ≤ 100 ms gate — **PASS**. Δ p50 = +24.3 ms. Cooperative abort (design D11) keeps live-path waiting at most one encoder forward pass (~187 ms on MPS per the spike in `docs/experiments/2026-04-24-refine-abort-spike.md`), so the shared `ASRModule._model_lock` contention never stalls a live batch for a full refine window.

- **Setup**: 4 synthetic pids × 30 s of Russian speech replayed at production cadence (one 3 s chunk per pid every 3 s) through a fresh `LiveTranscriber` + `PerSpeakerIngest` + (when enabled) `RefineWorker` with `abort_mode="cooperative"`. Warmup run before both measurements eliminates MPS cold-start bias. Baseline runs first, so any lingering thermal / swap pressure biases it in refine's favour — the reported +23.4 ms p95 regression is therefore a slight over-estimate if anything.

- **Per-chunk ratio = 1.00 on every pid**: every enqueued chunk produced exactly one `append_segment`, so the FIFO enqueue→append matching is exact (no empty-text drift). p95 (35/40 samples ≈ 88th percentile) = max in this sample size, so the 95th-percentile figure is "worst sample observed" rather than a true tail estimate.

- **Concurrent live recog service**: the bench ran with the production `recog-service.sh` live transcriber already loaded in another process (PID 73888, GigaAM on MPS). That adds some GPU scheduling contention to both runs symmetrically, but both configs share it, so the delta is not materially affected.

- **Does not unblock default-flip**: WER gate (Task 4) still missed the ≤ 25 % target, so `RECOG_PCM_REFINE` default stays `0`. Latency is not the bottleneck — refine is inexpensive *enough* to enable; the WER improvement just isn't large enough to justify default-on without real-meeting validation (plan §12.6).

### Known limitations

- **`/api/meetings/{id}/watch` does not receive `transcript_refine` WS frames** (latent, noted in Plan 3 review). Refine updates reach clients of this endpoint via `transcript_watcher`'s inode + size-shrink rewrite detection on `transcript.jsonl`, so the final refined text renders correctly, but the tier-1 → tier-2 animation path is only wired for live-stream clients (port 9080) via `frontend/bridge_subscriber.py`. Per-meeting viewers see segments flip in place on the next file-modify event instead of via a promoted WS message. Low priority — fixing would require adding a per-meeting client registry to `bridge_subscriber.py`.
- **Synthetic bench under-samples refine firings** (plan Task 4 observation §2): replay has no internal silence, so `SPEAKER_TURN_GAP=3 s` fires only at the trailing drain; the monolog cap (`PCM_REFINE_MONOLOG_CAP_S=15 s`) is the primary trigger in replay. Real meetings with natural turn-taking should exercise refine on virtually every closed reply, not just once per 15 s.
- **OpenSpec §12.1 (extended sanity filter) and §12.2 (POST runtime toggle)** are marked `[x]` per plan instruction but are only partially implemented — empty/identical-text guards in `_apply_refine` and watchdog-driven pause/resume from Task 1 cover the minimum viable intent; word-count-delta + Levenshtein gating and a `/api/pcm-diagnostics` runtime toggle are not wired.

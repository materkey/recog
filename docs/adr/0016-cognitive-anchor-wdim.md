# ADR-0016: Cognitive Anchor (WDIM) для восстановления контекста в live-режиме

## Status
Proposed

## Context

Live-транскрипт в Recog обновляется непрерывно (web UI + хранение в `meetings/`). Пользователь с СДВГ часто "выпадает" на 1-3 минуты и испытывает тревожность при попытке понять, что сейчас происходит. Скролл по длинной ленте текста создаёт дополнительную когнитивную нагрузку, особенно в моменте.

В проекте уже есть:
- Live view в `recog/web/static` с websocket потоком сегментов.
- Хранилище транскриптов в `recog/meeting_storage.py`.
- AI-провайдеры и промпты (ADR-0013), которые можно использовать для кратких summaries.
- Идея Bionic Reading (ADR-0015), которую можно применить для облегчения сканирования.

Нужен быстрый, локальный и малошумный способ "вернуться в контекст" за 3-5 секунд без социализированного "переспрашивания".

## Decision

### 1) Где живёт фича
MVP реализуется в web UI (страница Live) + backend endpoint в `recog/web/server.py`.
Chrome extension (KTalk) не трогаем в MVP, чтобы не усложнять доставку и не дублировать UI. Возможна интеграция позже.

### 2) Окно контекста
Используем "скользящее окно" по последним сегментам активной встречи:
- Основной критерий: последние `N` секунд (по `ts`), по умолчанию 180-300 секунд.
- Fallback: если нет таймстампов или окно пустое — последние `M` сегментов (например, 30-40).
- Ограничение по длине: max ~8-12k символов для экономии токенов.

### 3) Формат ответа от AI
Добавляем новый промпт `ANCHOR_PROMPT` и JSON-ответ со строгой схемой:

```json
{
  "current_topic": "короткая фраза про то, что обсуждают сейчас",
  "topic_tone": "neutral|calm|heated",
  "summary_bullets": [
    {"text": "ключевой факт/поворот", "ts_display": "HH:MM:SS"},
    {"text": "ключевой факт/поворот", "ts_display": "HH:MM:SS"},
    {"text": "ключевой факт/поворот", "ts_display": "HH:MM:SS"}
  ],
  "user_mentioned": true,
  "mention_context": "краткий контекст обращения",
  "mention_ts_display": "HH:MM:SS"
}
```

В промпт передаём:
- транскрипт с таймстампами `[HH:MM:SS] Speaker: text`
- имена локального участника (из `meeting.meta.participants`)

Если обращений к пользователю нет — `user_mentioned=false`, поля контекста пустые.

### 4) Backend API
Новый endpoint:
- `POST /api/live/anchor`

Параметры запроса:
- `window_seconds` (default 240)
- `max_segments` (default 35)
- `meeting_id` (optional)

Логика:
1) Определить текущую активную встречу (или по `meeting_id`).
2) Вычитать последние сегменты из `transcript.jsonl`.
3) Сформировать короткий transcript window.
4) Вызвать AI provider через `build_prompt(question="anchor", ...)`.
5) Вернуть JSON (валидация + fallback).

### 5) UI/UX (Live)
Добавить:
- Кнопку "Контекст" (иконка спасательного круга) в header live-страницы.
- Горячую клавишу `Alt+J` (для macOS допустимо `Option+J`) — не конфликтует с браузерными shortcuts.
- HUD-карточку поверх UI: затемнение фона, фокус на карточке.
- Закрытие: `Esc` или клик вне карточки.
- В каждой буллете рядом компактный таймштамп-ссылка: скролл к ближайшему сегменту в live ленте.
- В футере: индикатор "вас упоминали / не упоминали" + контекст.

Опционально (V2): применить BioRead (ADR-0015) к тексту буллетов.

### 6) Приватность
WDIM работает локально для пользователя и не отображается другим участникам. Никаких данных не сохраняется в `meetings/`.

## Implementation Plan (scope)

| Шаг | Файл | Изменение |
|-----|------|-----------|
| 1 | `recog/web/ai_provider.py` | Добавить `ANCHOR_PROMPT`, расширить `build_prompt()` |
| 2 | `recog/web/server.py` | Добавить `AnchorRequest/Response`, endpoint `/api/live/anchor` |
| 3 | `recog/web/static/index.html` | Добавить кнопку и разметку HUD |
| 4 | `recog/web/static/app.js` | Hotkey, вызов API, рендер карточки, скролл к сегменту |
| 5 | `recog/web/static/style.css` | Стили для overlay/HUD |
| 6 | `recog/web/static/utils` (опц.) | BioRead для буллетов |

## Consequences

### Positive
- Быстрое восстановление контекста без скролла и стыда "переспрашивать".
- Минимальные изменения в pipeline: используется существующий AI слой.
- Работает для всех источников (KTalk, mic, system audio), т.к. опирается на `meeting_storage`.

### Negative
- AI может ошибаться или упускать детали.
- Дополнительные расходы на токены и задержка ответа 1-3 сек.
- Если выбран OpenRouter, контекст уходит во внешний API.

### Mitigations
- Жёсткая схема JSON + fallback на "последние N сегментов".
- Ограничение окна и rate-limit на кнопку (например, 1 запрос в 10 сек).
- Явный индикатор "summary may be approximate".

## Alternatives Considered

1) Только эвристическое суммирование без AI
   - Быстро и бесплатно, но качество низкое и не решает когнитивную задачу.

2) Встраивание в KTalk extension
   - Улучшит UX для KTalk, но усложняет деплой и требует отдельной авторизации к AI.

3) Проактивные подсказки по idle-детекту (V3)
   - Полезно, но требует точного UX, чтобы не раздражать.
